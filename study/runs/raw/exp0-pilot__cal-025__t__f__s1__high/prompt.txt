# ThoughtML specification

# ThoughtML — a guide for the AI that writes it

You are most likely the author. ThoughtML is a plain-text language for recording
**reasoning you keep** — claims, evidence, decisions, and how they change over time —
as a graph a machine can read back. It is written far more often by an AI agent
transforming prose (a report, a case study, a debate, a postmortem, a decision) into
structured thought than by hand. This file is the whole language in one place: read it
once and you can author correct ThoughtML and interpret everything the toolchain gives
back. It is the exact spec the `thoughtml guide` command prints and the site serves — one
source, so it cannot drift from the tool.

The single governing idea: **ThoughtML is a mirror, not an oracle.** It does not decide
for you. It reflects the reasoning you put in — and *surfaces where that reasoning
disagrees with itself*: a confidently-held claim your own evidence defeats, or one belief
defined two incompatible ways. Your job when authoring is to record the reasoning
faithfully so the mirror stays honest. The fastest way to break it is to **overstate** —
e.g. use an evidence relation to write a plain list. The rules below exist to prevent
exactly that.

Everything here is derived from the reference parser's vocabulary and compute code, not
from prose docs. The closed sets (kinds, relations, fields, postures) are **exhaustive** —
if a word is not listed, it does not exist, and inventing one earns a warning (or, worse,
silently changes how a line parses). When unsure, prefer the smaller, more literal
construct.

---

## 1. The 60-second model

A document is a flat or nested list of **records**, one per header line, each with an
indented block beneath it. There are six things you can record:

- **focus** — a node you reason about (a claim, an observation, an option, a goal…).
- **question** — an open question the document is trying to resolve.
- **link** — a typed, directed edge between two nodes (`X supports Y`).
- **stance** — an *agent's* attitude toward a node or edge (the only place `confidence` lives).
- **scope** — a named container grouping related records.
- **profile / import** — advanced: dialect extensions and multi-document namespaces.

From these, the toolchain **derives** readings you never write by hand: a confidence
propagated along evidence, a grounded argument status (which claims survive attack), a
timeline, expected values over a decision, and a **conflict report** (the mirror). You
author the graph; you read back the derived readings (§13). Nothing is computed until you
ask (`--compute` / `--audit`).

Nothing is ever deleted. A superseded belief, an abandoned branch, a divergent
redefinition — all are kept with their reason. **"Fold, don't forget."**

---

## 2. Syntax rules

- **Indentation is structure.** A record's block is the lines indented under its header.
  Nesting a record under a `scope`/`focus`/`question` makes it a *member* (§9). Use
  consistent spaces.
- **Ids are `lowercase-kebab-case`** — `[a-z][a-z0-9-]*`, starting with a letter:
  `cache-is-safe`, `error-rate-up`. One id = one node; mentioning an id again *merges*
  into that same node (§8). A namespaced reference is `ns.id` (only after `import`, §9).
- **Comments are whole-line only**: a line whose first non-space character is `#`. There
  are **no** trailing/inline comments — `focus x  # note` is not a comment, it's a parse
  error.
- **A header is one line**; its body prose, `field value` lines, `= formula` lines, and
  nested records follow, indented.
- **Body prose** is an indented line that is neither a `field` (`name value…`), a
  `= formula`, nor a nested header — it becomes the node's description. Write bodies as
  ordinary sentences (a leading capital or trailing punctuation keeps an all-lowercase
  line from being misread as a field). First mention of a body wins on merge.

Minimal shape — two typed foci and a link, so nothing dangles (strict-clean):

```thml
focus load-test-passed
  kind observation
  Held p99 under 2x peak traffic.

focus cache-is-safe
  kind claim
  Safe to ship the new cache layer today.

link load-test-passed supports cache-is-safe
```

---

## 3. Records and headers

The **first word** of a header decides what it is: seven reserved header keywords, plus
three sugar forms.

| Header form | Makes | Example |
|-------------|-------|---------|
| `focus <id>` | a focus | `focus cache-is-safe` |
| `question <id>` | a question | `question cause-of-shift` |
| `link [alias:] <from> <rel> <to>` | a link | `link load-test supports cache-is-safe` |
| `stance <agent> <posture> <target>` | an agent stance (longhand) | `stance payments-agent holds root-cause` |
| `scope <id>` | a container | `scope incident-742` |
| `profile <name>` | a dialect (advanced, §5/§6) | `profile appsec` |
| `import <name> as <ns>` | a namespace (advanced, §9) | `import inspection-standards as standard` |
| **`<kind> <id>`** (typed header, sugar) | a focus with that kind | `observation error-rate-up` |
| **`<relation> <target>`** (evidence bundle, sugar) | many links | see §10 |
| **`<agent> <posture> …`** (readable action) | a stance (+ maybe a focus/link) | `team noticed shift` |

If a header's first word is a **kind** (§5) it's a typed focus; if it's a **relation**
(§6) it's a bundle; otherwise it's read as an `<agent> <posture> …` action (§7) — and the
**second** word must then be a posture, or the line errors (`unknown record kind or
header`). So the first word (and an action's second word) is overloaded across the closed
sets — which is why inventing a kind / relation / posture doesn't merely warn, it can
change how a line parses. (`stance` longhand and the readable `<agent> <posture>` form
build the *same* stance object; use whichever reads better — `grant-panel` and
`bridge-inspection` mix both to prove it.)

---

## 4. What can be linked

A link's `from`/`to` may resolve to a **focus, question, or link** (yes, links can target
links — that's how `undercuts` attacks an inference). Targeting a **stance** or **scope**
is an error (`TML202` — "links may only connect …"). Targeting an id that doesn't exist
yet is a warning (`TML201` unresolved reference) — declare it or fix the typo.

---

## 5. Foci and the ten kinds

A focus's `kind` is its semantic category. Set it with a `kind` field, a typed header
(`claim cache-is-safe`), or let a posture infer it (§7). The **ten** kinds are exhaustive:

| Kind | Meaning | Typically introduced by |
|------|---------|-------------------------|
| `observation` | Something seen or measured | `noticed`, or a typed header |
| `claim` | An assertion put forward as true | `infers`, or a typed header |
| `hypothesis` | A proposed explanation, not yet settled | typed header |
| `option` | A choice on the table | `considers`, or a typed header |
| `decision` | A choice to be made or recorded | `holds` / `chooses` |
| `outcome` | A result an option `leads-to` | edge inference, or a typed header |
| `goal` | A desired end | typed header |
| `assumption` | Something taken as given | typed header |
| `memory` | A recollection carried forward | `remembers` |
| `action` | A thing one *does* — a plan, intervention, mitigation | typed header only (no posture infers it) |

An unknown kind warns (`TML101`, with a nearest-spelling suggestion) unless a `profile`
declares it (§6). Two *explicit* kinds disagreeing on one focus keeps the first and warns.

## 6. Relations — the fourteen edges (READ THIS TWICE)

Relations are the heart of the language and the easiest thing to get wrong. Grouped by
role. **Only the first three carry evidence polarity** — they, and *only* they, move
derived confidence and argument status (§13).

### Evidence (defeasible — these move the numbers)
| Relation | Polarity | Use for |
|----------|----------|---------|
| `supports` | **+** | source is *evidence for* target |
| `opposes` | **−** | source rebuts a *node*: "that claim is false" |
| `undercuts` | **−** | source attacks an *inference*: "that step doesn't follow" (target is usually a **link**) |

### Structural & causal (no polarity — describe, don't argue)
| Relation | Meaning |
|----------|---------|
| `causes` | source brings about target (expected acyclic) |
| `enables` | source makes target possible |
| `prevents` | source stops target |
| `depends-on` | target is required for source (expected acyclic) |
| `blocks` | source holds target up (what `until … answered` desugars to, §16) |
| `answers` | source *resolves* a question (the one settled answer) |
| `revises` | source supersedes target (nothing deleted; §11) |

### Decision
| Relation | Meaning |
|----------|---------|
| `leads-to` | an option leads to an outcome; carries a `probability` |
| `option-of` | an option belongs to a decision |

### Membership & candidacy (non-evidential — how you list things)
| Relation | Meaning |
|----------|---------|
| `part-of` | source is *one item in* the target collection |
| `candidate-for` | source is a *proposed* answer to a question (not resolved) |

**The mistake that breaks the mirror.** To *list* the items of something — SWOT strengths,
competitors, success factors, sub-points, friction points — use **`part-of`**, never
`supports`. `supports` means "evidence this is true," so enumerating a claim's parts with
it silently inflates that claim's confidence: "Netflix has strengths" reads as
100%-certain just for *naming* them. `part-of` has no polarity, so enumerations stay
structure and the numbers keep meaning something. Likewise use `candidate-for` for a
question's proposed options and reserve `answers` for the one that actually resolves it.
(`grant-panel` and `inspection-standards` show `part-of` done right;
`why-the-loaf-failed` shows `candidate-for` vs `answers`.)

**Other easy confusions:**
- `opposes` (a claim is false) vs `undercuts` (a step doesn't follow — target the **link**).
  `peer-review` sets them side by side.
- `weight` (evidential strength, any evidence/structural link, `0..1`) vs `probability`
  (outcome likelihood, `leads-to` **only**, `0..1`). Putting one where the other belongs
  is ignored with a warning.
- `answers` doubles as a **field** and a **relation**: as an indented line,
  `answers <question>` on a stance/focus points it at the question it settles.
- There is **no** `rejects` or `mitigates` relation in the core. A hard rejection is
  `opposes`; defending X is attacking X's attacker (`guard opposes risk`). (`rejects`
  exists only as a *posture*, §7. A domain that truly wants `mitigates` declares it in a
  `profile` — see `bridge-inspection`.)

**Profiles add relations (and kinds/fields/postures).** A `profile` header opens a dialect
whose declared words are then legal below it; anything it doesn't declare still warns.
Comma-separated lists:

```thml
profile structural
  kinds defect, remedy
  relations aggravates, mitigates
  fields severity, next-inspection
  postures certifies
```

One scoping rule: a posture a profile adds is reachable only through the `stance`
longhand. The readable `<agent> <posture> …` form is resolved against the twelve core
postures before any profile is consulted.

## 7. Stances and the twelve postures

A **stance** is an agent's attitude toward a node or edge — the only place a `confidence`
lives. You almost never write `stance` longhand; you write the readable form **`<agent>
<posture> <target>`**, where `<agent>` is any id you choose (`team`, `analyst`, `oncall`,
`classifier`). The **twelve** postures are exhaustive:

| Posture | Creates | Kind inferred | Shape |
|---------|---------|---------------|-------|
| `noticed` | focus + stance | `observation` | `team noticed metric-shift` |
| `considers` | focus + stance | `option` | `team considers rollback` |
| `holds` | focus + stance | `decision` | `team holds rollback-decision` |
| `chooses` | focus + stance | `decision` | `team chooses option-a` |
| `remembers` | focus + stance | `memory` | `team remembers last-outage` |
| `infers` | `claim` focus + `supports` links from the listed sources + stance | `claim` | `team infers X from a b c` |
| `suspects` | a **link** (`from rel to`) + a stance over it | — | `team suspects deploy causes shift as deploy-cause` |
| `asks` | a stance on an (existing) question | — | `team asks cause-of-shift` |
| `doubts` | a stance | — | `team doubts vendor-claim` |
| `accepts` | a stance | — | `team accepts postmortem` |
| `rejects` | a stance (rules a target out) | — | `team rejects option-b` |
| `revises` | a stance superseding this agent's *prior* stance on the target | — | `analyst revises on-track-claim` |

Confidence and rationale ride on the stance: put `confidence`, `note`, `because`, and
`asserted-at` in the block under a posture line. `confidence` may be a scalar
(`confidence 0.72`), a **range** (`confidence 0.25..0.70`, read at its midpoint), or
genuinely **unknown** (`confidence ?` — see `dating-the-codex`). `suspects` takes a full
edge (`<from> <relation> <to> [as <alias>]`); `infers` takes `<target> from <id> <id> …`
and wires each source with a `supports` link, so the reasoning is explicit.

**Which postures declare a node vs. only reference one** (this decides strict-clean, §12):
the focus-creating postures declare their *target*; `suspects` declares *both* endpoints
of its edge; `infers` declares only its *target* — its **sources** are `supports`
endpoints you must declare elsewhere. `asks` / `doubts` / `accepts` / `rejects` /
`revises` create *only* a stance, so **their target must already exist**, or you get an
unresolved-reference warning.

---

## 8. Merging — one id, one node

An id mentioned more than once is **one** node; the mentions merge. `body`, `quantity`,
`formula` are first-wins; `fields` accumulate; `kind` follows priority (explicit >
posture-inferred). This lets you define a focus once in full, then refer to it by id
anywhere — including from another agent's stance, or a later scope.

**Divergence is kept, not dropped.** If a later mention gives a *different*
body/quantity/formula (not a repeat), the alternative is retained on the node and the
mirror raises a `definition-divergence` conflict (§13). Concurrent authors never clobber
each other — see `peer-review`, where two referees write one `central-claim` two
ways and both survive.

---

## 9. Scopes, thought-trees, and imports (nesting)

Indent records under a `scope` to group them, or under a `focus`/`question` to make a
**thought-tree** — a claim (or question) and the reasoning that hangs off it, as one unit.
Nested members are recorded on the container's `includes` and **inherit its provenance and
temporal context** — an explicit value on the child wins. (`well-water` puts `source`
and `observed-at` on a scope and lets the observations inherit; `grant-panel` nests its
options and questions inside one scope.)

```thml
focus ship-decision
  kind decision
  Ship the new cache layer this week.

  observation load-test-passed
    p99 held under 2x peak traffic.

  assumption rollback-ready
    One-command rollback is wired up.
```

**Imports (multi-document).** `import <file> as <ns>` pulls another document's nodes in
under a namespace; you then reference them as `ns.id`. The importer is checked as a
**project** (importer + library together) so cross-document references resolve. A library
must itself be strict-clean as a standalone document. See `inspection-standards` (the
library) and `bridge-inspection` (`import inspection-standards as standard`, then
`depends-on standard.load-rating-on-record`).

## 10. Numbers, provenance, formulas, and evidence bundles

**Ranges & clamping.** `confidence` / `weight` / `probability` are `0..1`. `weight` and
`probability` outside that range are **clamped** with a warning (`TML402`). `confidence`
is *not* clamped: it accepts a scalar, an ordered range `low..high` (unordered → error),
or `?` for genuinely unknown. `quantity` is a typed measure with a unit (`quantity 30 GB`).

**Provenance basis.** Any number may declare *how it was arrived at*, inline, from the
exhaustive set `measured` / `estimated` / `assumed`:

```thml
focus disk-headroom
  kind observation
  Free space on the primary volume.
  quantity 30 GB measured

focus volume-is-healthy
  kind claim
  The volume has room for this quarter's growth.

link disk-headroom supports volume-is-healthy
  weight 0.85 estimated

ops holds volume-is-healthy
  confidence 0.9 assumed
```

A number with no basis is silent about it; the opt-in `--strict-provenance` lint flags the
omission (`TML401`). Prefer stating a basis — an unbased number reads as fact without
saying on what footing it stands.

**Formulas (`= expr`).** A focus can compute its `quantity` from other foci with a
`= expression` line over `+ - * /` and referenced ids. The parser **checks units** as it
goes (USD/hour × hour = USD; USD ÷ user = USD/user), so a dimensional mistake is caught,
not shipped. `--compute` evaluates them into `computed_quantity`. See `orchard-water` (a
self-computing water budget) — change one input and the whole thing recomputes.

```thml
observation well-yield
  quantity 30 L/min measured
observation pump-window
  quantity 480 min measured
claim daily-supply
  = well-yield * pump-window
```

`daily-supply` computes to `14400 L` — `L/min × min` is unit-checked to `L`, so a
dimensional slip is an error, not a silent wrong number.

**Evidence bundles** collapse the common "many sources → one target" repetition. A bare
`<relation> <target>` header lists sources one per line, each `<source> [weight <n>]
[basis]`, each desugaring to an ordinary link:

```thml
supports customer-pain-points
  late-fees-problem      weight 0.90 assumed
  limited-availability   weight 0.85
  long-travel-time
```

Bundles work with **any** relation — including `part-of` and `candidate-for`, the
idiomatic way to write a collection:

```thml
part-of netflix-strengths
  strong-global-brand
  large-subscriber-base
  advanced-algorithms
```

**A bundle links; it does not declare.** Every member id *and* the bundle target must be a
node declared somewhere (a `focus`/typed header/`question`, or a focus-creating posture).
An id that appears only inside a bundle is an unresolved reference and warns — so it breaks
strict-clean. Declare the nodes first (see gold example B, §15), then bundle them.

## 11. Time — optional, and how belief changes

**Time is optional. Do not invent timestamps to force an ordering.** A dateless document
parses and renders fine — the viewer reveals it in *document order* (narrative replay).
Reach for dates only when *when* actually matters.

When it does, three ISO-8601 fields (partial dates like `2026` or `2026-06` are fine):

- `observed-at` — when something was seen.
- `asserted-at` — when a belief was put on the record.
- `valid-during <start>..<end>` — a span over which something holds (`dating-the-codex`).

**Lifecycle (`status`).** A focus can carry a `status`: `open` (default, live), `settled`
(resolved), `superseded` (replaced by a later belief), `abandoned` (a dead end). A
settled/superseded/abandoned branch is kept with its reason and folds in the viewer —
never deleted. (`grant-panel` parks a withdrawn option as `abandoned`;
`dating-the-codex` walks a dating through `superseded`.)

**Revision.** `link new revises old` supersedes a *node*; the `revises` posture supersedes
the same agent's *prior stance*. Either way the old belief stays in the graph (it just
stops counting as live evidence). A revision asserted *earlier* than what it revises warns
(`TML304`).

**Replay.** `--as-of <time>` (valid-time) or `--as-of-seq <n>` (recording order) projects
the document to a moment: later beliefs — and the edges that depended on them — drop out,
and supersession and the audit recompute as of that instant.

## 12. The strict-clean contract — your feedback loop

This is the most important operational rule. **A good ThoughtML document is
"strict-clean": zero errors AND zero warnings.** Treat that as a fitness function — author,
run the parser, read the diagnostics, fix, repeat until clean. Every one of the 10 corpus
examples is strict-clean; aim for the same.

Run the reference CLI (`thoughtml <file>`); it prints diagnostics with source lines and
exits nonzero under `--strict` if any warning remains. Useful flags on the bare invocation:

| Flag | What it does |
|------|--------------|
| (none) | parse + validate; emit the canonical JSON model |
| `--strict` | treat warnings as failures (use this as your gate) |
| `--compute` | the whole second reading: derived confidence, argument status, sensitivity, formulas, decision EV, audit |
| `--audit` | just the conflict report (the mirror's headline) |
| `--as-of <t>` / `--as-of-seq <n>` | replay as of a valid-time / a recording step (§11) |
| `--html` | bake a standalone interactive viewer (for humans, not you) |
| `--ast` | emit the surface AST instead of the canonical model |
| `--strict-provenance` | also warn on numbers with no basis |

**Subcommands — the rest of the toolchain** (the bare invocation still works):

| Command | What it does |
|---------|--------------|
| `thoughtml guide [topic] [--full]` | this language, from the binary: a one-screen tour, one section, or `--full` |
| `thoughtml check <f> --json` | validate → diagnostics as JSON with a **stable code, line, and suggested fix** per issue. *This is your self-correction loop:* emit → `check --json` → apply the `help` fixes → repeat until clean. Add `--lint` for the `supports`-as-a-list smell (`TML501`). |
| `thoughtml fmt <f>` | rewrite in the one canonical style (`-w` in place, `--check` for CI); re-parses its own output and never changes the model |
| `thoughtml explain <f> <id>` | trace why a node has its confidence/status — evidence for/against, each edge's leverage, the conflict it's caught in |
| `thoughtml diff <a> <b>` | a **belief-level** diff: what flipped `in`/`out`, which confidences moved, which conflicts appeared/resolved |
| `thoughtml stream <f> [--json]` | host a live read-only view from the editing computer; watches the entry and imports, keeps the last valid graph during errors. Loopback-only by default; `--lan` shares on a trusted local network |

Install with `cargo install thoughtml` (or `npm install -g thoughtml`).

**The diagnostic codes** are a stable contract, grouped `1xx` vocabulary, `2xx` references,
`3xx` graph coherence, `4xx` numbers, `5xx` lints:

| Code | Means | Fix |
|------|-------|-----|
| `TML101` | unknown focus kind | use a real kind (§5) or declare it in a `profile` |
| `TML102` | unknown relation | use a real relation (§6) or declare it in a `profile` |
| `TML103` | unknown posture | use one of the twelve (§7) |
| `TML104` | unknown field | use a known field (§16) or declare it in a `profile` |
| `TML105` | a known field the record cannot act on | move it to the record it belongs on — e.g. `expects`/`about` onto a `question`, `until` onto the node being blocked |
| `TML201` | unresolved reference | an id in a link/stance/bundle doesn't exist — declare it or fix the typo |
| `TML202` | links may only connect foci/questions/links | you targeted a stance or scope |
| `TML301` | focus not connected to anything | link it in, nest it, or drop it — every node must earn its place |
| `TML302` | contradictory stances | one agent took clashing postures on one target (`accepts`+`rejects`) — reconcile or `revises` |
| `TML303` | cyclic dependency | a cycle in `causes`/`depends-on` — break it |
| `TML304` | revision asserted earlier than its target | check your `asserted-at` ordering |
| `TML305` | malformed decision subgraph | a `leads-to` self-loop, or an option missing from the EV ranking |
| `TML401` | number declares no basis | add `measured`/`estimated`/`assumed` (only under `--strict-provenance`) |
| `TML402` | weight/probability outside `0..1` | it was clamped — use a value in range |
| `TML501` | `supports` used as a list (lint) | if these are items not evidence, use `part-of` (§6) — fires at ≥3 supports with no counter-evidence |
| `TML502` | circular justification (lint) | a `supports` loop: the claims inside it derive confidence from no outside evidence — give one of them real evidence, or merge them if they are one belief said twice |

`TML101`–`TML104` come with a nearest-spelling suggestion. `TML105` is the guard against a *silent* loss: a known field in the wrong place used to be accepted and then ignored, so a document could stay strict-clean while dropping what its author wrote. Nothing the parser understands is discarded quietly. (Note: the `definition-
divergence` audit conflict and the decision-EV warnings carry no TML code — they surface in
`--audit` / `--compute`, not as validation diagnostics.)

## 13. Reading a document back — the mirror is YOUR interface

You do **not** need to look at the rendered graph; the SVG viewer is for humans. Your view
is the **textual** output of `--compute` / `--audit`. Read these fields to understand a
document — yours or one handed to you. The mechanics are exact and worth knowing so you can
interpret the numbers:

- **`derived_confidence`** — belief propagated along `supports`/`opposes`/`undercuts`. Each
  node's value is `logistic(2.0 × Σ polarity·weight·believedness)` over its incoming
  evidence edges, where `logistic(x)=1/(1+e⁻ˣ)`, polarity is `+1` for `supports` / `−1` for
  `opposes`/`undercuts`, `weight` defaults to **0.5** if unstated, and a source's
  *believedness* is its own derived confidence (transitive), else its authored confidence,
  else `1.0`. No evidence → `0.5` (neutral). Rounded to 3 decimals. So a single strong
  support (`weight 0.85`, full-strength source) yields ≈0.85. **If a claim you'd expect to
  be shaky reads near-certain, suspect a list written with `supports`** (§6).
- **`argument_status`** — grounded labelling (Dung) over the attack graph. A node is `in`
  iff **every** attacker is `out`; `out` iff **some** attacker is `in`; otherwise
  `undecided` (e.g. a mutual attack). Attacks are `opposes` and `undercuts`; defense is
  just attacking an attacker. Only nodes touched by an attack get a status.
  (An `undercuts` edge whose target is a **link** doesn't rebut a node — it cuts that
  inference's weight by `1 − undercut_weight`, so premises flow through a weakened step.)
- **`leverage`** (sensitivity) — how load-bearing each piece of evidence is; what the
  conclusion actually hangs on.
- **decision EV** (`--compute`, over `leads-to`/`option-of`) — an option's expected value is
  `Σ probability·payoff` over its `leads-to` edges. **Payoff** is the outcome's
  `computed_quantity` (a formula) or authored `quantity`, in base units; all payoffs within
  one option must share a dimension. **Probability** is the edge's authored `probability`, or
  — if omitted — the outcome's own `derived_confidence` (belief becomes likelihood, once and
  visibly). Options are **ranked** high-to-low under their decision but **no winner is
  crowned** — it reports, you decide. (`evacuate-or-shelter` is the full worked case,
  including a what-if that flips the ranking.)
- **`timeline`** — the ordered `events` array (by valid-time, `seq` tiebreak).
- **`conflict report`** (`--audit`) — **the headline.** Where structure disagrees with the
  author. Exactly two conflict types:
  - `confidence-vs-status` — a **stance's** confidence contradicts its target's grounded
    status. Two asymmetric cases: high confidence **≥ 0.66** in a claim the structure
    **defeats** (`out`) is an **error**; low confidence **≤ 0.34** in one that **survives**
    every attack (`in`) is a **warning**. Needs both an attack (`opposes`/`undercuts`)
    giving the target a status *and* an authored `confidence` on it. This is the flagship —
    `pour-the-slab`.
  - `definition-divergence` — one id defined two different ways (§8); a **warning**.

When you transform prose into ThoughtML, run `--audit` afterward and check the conflicts
are the *real* ones in the source — not artifacts of enumerations you wrote as evidence. A
clean, meaningful conflict report is the sign you modeled the reasoning faithfully.

**What the mirror cannot see.** It checks a document against *itself*, never against the
world, and a falsification pass over it (`tests/falsification.rs`) pins exactly where that
stops. Four errors produce a clean report and confident numbers:

- **A false premise.** `earth-is-flat supports maps-are-wrong` is valid reasoning from a
  nonsense premise. Nothing in the model can know it is nonsense; the conclusion derives
  ≈0.73 all the same.
- **One fact entered twice.** Two ids for one underlying observation both support the same
  claim. Independence is assumed and never checked, so the evidence compounds — ≈0.96 from
  a single survey cited twice.
- **Evidence never written down.** A document records what its author chose to record. Two
  failed trials omitted leaves a perfectly coherent graph reading ≈0.86.
- **Circular justification**, until you ask. `a supports b`, `b supports a` derives >0.5 for
  both from no outside evidence. This one *is* visible in the graph, so `check --lint`
  reports it as `TML502` — but it is off by default, like every modelling lint.

The first three are not bugs to fix; they are the boundary of what a self-consistency check
can do. They are the reason the mirror reports and never decides. **Your job as the author
is the part the tool cannot do: write down the evidence that cuts against you.**

## 14. Authoring checklist (the distilled rules)

1. **Only closed-set words.** Kinds (§5), relations (§6), postures (§7), fields (§16) are
   exhaustive. Never invent one — it warns (or reparses the line). When unsure, use the most
   literal; if a domain truly needs new words, declare a `profile`.
2. **Lists use `part-of`, not `supports`.** Evidence relations move confidence; reserve them
   for genuine evidence. This is the #1 way to corrupt the mirror.
3. **`candidate-for` for proposed answers; `answers` only for the resolved one.**
4. **`opposes` a claim, `undercuts` an inference** (target the link). `weight` for evidence,
   `probability` for `leads-to` only.
5. **Don't date to sort.** Time is optional; document order already orders. Date only when
   *when* matters.
6. **State a basis** (`measured`/`estimated`/`assumed`) on numbers you can; use `confidence
   ?` when you genuinely don't know.
7. **One id = one node**, and **every link/bundle endpoint must be a declared node** — a
   bundle references, it doesn't create. Define once in full, reference by id everywhere.
8. **Record dead ends, don't drop them** — `status abandoned`/`superseded` with a reason.
9. **Gate on strict-clean.** Iterate until `--strict` passes, then read `--audit` and confirm
   the conflicts are the real ones.
10. Prefer **typed headers** (`claim x`) and **bundles** (`part-of group` + members) — same
    model, far less boilerplate.

## 15. Gold examples, and the corpus (one worked instance of everything)

Two full strict-clean documents inline; then an index of all 10 corpus files, each a
canonical instance of one construct. To learn a feature, read the file named beside it.

**A. The flagship — clean in form, caught by the mirror (`pour-the-slab`):**

```thml
focus conditions-are-fine
  kind claim
  Conditions on site are fine to pour the foundation slab this afternoon.

focus truck-is-booked
  kind observation
  The ready-mix truck is booked for 14:00 and the full crew is on site.
  source site-diary
  observed-at 2026-03-11

focus overnight-freeze
  kind observation
  The site thermometer logged minus four degrees from 02:00 to 06:00, and tonight's
  forecast repeats it. Fresh concrete that freezes before it sets never recovers.
  source site-diary
  observed-at 2026-03-11

link truck-is-booked supports conditions-are-fine
link overnight-freeze opposes conditions-are-fine

site-engineer holds conditions-are-fine
  confidence 0.88 assumed
  note Pouring today. The truck is booked and the crew moves to another job Thursday.
```

Zero errors, zero warnings — the *form* is perfect. But `--audit` reports a
`confidence-vs-status` **error**: `site-engineer` holds the claim at 0.88 while their own
`overnight-freeze` evidence defeats it (`argument_status: out`). The mirror shows the
conflict; it does not decide.

**B. Dateless analysis — declare nodes, then bundle. `part-of` (structure) never inflates,
`supports` (evidence) does; `candidate-for` proposes without resolving:**

```thml
claim eliminate-late-fees-was-key
  Removing late fees was the decisive early move.
observation customer-hated-late-fees
  Late fees were the top customer complaint.
observation subscription-model-proven
  Flat-rate rental had already shown demand.

# evidence -> supports (raises derived_confidence)
supports eliminate-late-fees-was-key
  customer-hated-late-fees   weight 0.9 estimated
  subscription-model-proven  weight 0.7 assumed

claim netflix-strengths
  Netflix's core strengths.
observation strong-global-brand
  Recognized worldwide.
observation large-subscriber-base
  Hundreds of millions of members.

# structure -> part-of (no confidence inflation on netflix-strengths)
part-of netflix-strengths
  strong-global-brand
  large-subscriber-base

question most-impactful-strategy
  Which strategy mattered most?
  expects claim

# proposed answers -> candidate-for (not the resolved `answers`)
candidate-for most-impactful-strategy
  eliminate-late-fees-was-key
  netflix-strengths
```

Under `--compute`: the `supports` bundle raises `eliminate-late-fees-was-key` to ≈0.96; the
`part-of` bundle gives `netflix-strengths` **no** derived confidence at all; the conflict
report is empty because nothing overstates. Swap the `part-of` for `supports` and
`netflix-strengths` would falsely read near-certain — the exact pollution to avoid.

**The corpus — concept → file** (all in `examples/`, all strict-clean, all `fmt`-clean):

*Start here (small, complete):*
- `pour-the-slab` — the flagship: clean in form, and `--audit` still catches it (example A above).
- `why-the-loaf-failed` — an everyday question done right: `candidate-for` proposes, `answers` resolves; `asks`, `suspects` (edge + `as` alias), `hypothesis`, a `status abandoned` dead end kept with its reason.

*Argument structure (the attack graph):*
- `peer-review` — `undercuts` (attack an inference, with a `link alias:`) vs `opposes` (attack a claim); a confidence **range**, `because`, and the second mirror conflict: `definition-divergence`, two referees writing one id two ways, both kept.
- `well-water` — a field investigation as an acyclic `causes`/`enables`/`prevents` graph; a `scope` whose provenance the members inherit; a weighted `supports` bundle; `noticed`/`infers`/`suspects` and `-by` attribution.

*Time, lifecycle, and change:*
- `dating-the-codex` — a belief `revises`d: `status superseded`, `valid-during`, `asserted-at`, a `memory` with a `source`, `confidence ?`, and `--as-of` replay that makes a conflict disappear because it did not exist yet.

*Structure vs. evidence, and decisions:*
- `grant-panel` — one award, four agents: a `part-of` criteria collection (not `supports`), `option-of`, `considers`/`chooses`/`rejects`, `stance` longhand with an alias, `about`, `until … answered` (→ `blocks`), an `abandoned` proposal.

*The compute layer (`--compute`):*

*Extensibility (the import pair):*
- `inspection-standards` — a standalone, importable library: a `part-of` collection of `claim`s, `enables`, `depends-on`, a budget `quantity`.
- `bridge-inspection` — `import inspection-standards as standard`, referencing `standard.<id>`, checked as a project; plus a `profile` (`structural`) adding domain kinds/relations/fields/postures.

Between them they carry a worked instance of all ten kinds, all fourteen relations, all

and both audit conflicts — pinned by a test, so this list cannot quietly go stale.

## 16. Quick reference (everything, at a glance)

**Header keywords (7):** `scope` `question` `focus` `link` `stance` `profile` `import`
(+ sugar: typed-focus `<kind> <id>`, bundle `<relation> <target>`, action `<agent> <posture> …`).

**Kinds (10):** `observation` `claim` `hypothesis` `option` `decision` `outcome` `goal`
`assumption` `memory` `action`.

**Relations (14):** evidence → `supports` `opposes` `undercuts`; structural/causal →
`causes` `enables` `prevents` `depends-on` `blocks` `answers` `revises`; decision →
`leads-to` `option-of`; membership → `part-of` `candidate-for`.

**Postures (12):** `noticed` `considers` `suspects` `infers` `asks` `holds` `chooses`
`rejects` `revises` `remembers` `doubts` `accepts`.

**Field placement.** Most fields ride on whatever record you put them under, but three
are scoped, and using them elsewhere is `TML105`: `expects` and `about` belong to a
`question`, and `until <id> [state]` — sugar for a `blocks` edge — belongs on the thing
being blocked (a focus, a question, or a stance; **not** a link, scope, bundle, or profile,
none of which is a node that can be held up). A `profile` block takes *only* `kinds`,
`relations`, `fields`, `postures`.

**Fields:** `note` `kind` `quantity` `about` `weight` `probability` `confidence` `because`
`answers` `expects` `status` `until` `source` `observed-at` `asserted-at` `valid-during`
`noted-by` `noticed-by` `suspected-by` `chosen-by` `blocked-by` `undercut-by`
(+ profile-only: `kinds` `relations` `fields` `postures`). Plus `= <expr>` formula lines.

**Number bases (3):** `measured` `estimated` `assumed`.  **Status (4):** `open` `settled`
`superseded` `abandoned`.  **Confidence:** scalar, `low..high` range, or `?`.

**Compute (`--compute`):** `derived_confidence = logistic(2.0 · Σ polarity·weight·believedness)`,
default `weight` 0.5, no-evidence 0.5; `argument_status` = grounded (`in` iff all attackers
`out`); decision EV = `Σ prob·payoff`, prob falls back to derived confidence.

**Audit (`--audit`):** `confidence-vs-status` (≥0.66 vs `out` = error; ≤0.34 vs `in` =
warning) and `definition-divergence`.

**Diagnostic codes:** `1xx` vocabulary · `2xx` references · `3xx` graph coherence · `4xx`
numbers · `5xx` lints (`TML501` = `supports`-as-a-list).

**The two rules that matter most:** lists are `part-of`, not `supports`; gate on
strict-clean, then read `--audit`.
