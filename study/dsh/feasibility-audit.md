## Integration surface

The supported headless profile creates a fresh persisted session, submits one
task, waits for quiescence, flushes the session, prints the final assistant text,
and exits. It does not expose the complete event stream on stdout. DSH's standard
`session/event` and tool events are therefore the candidate measurement surface.
A study plugin should listen to standard events and write a separate experiment
log; it should not add custom durable session-event types.

The matched Markdown and ThoughtML state tools are external plugins layered over
the fixed profile. This avoids creating a competing harness or changing the
agent loop. The plugin/configuration route has now passed an offline mock
composition under all three study conditions.

The default composition includes a telemetry exporter URL, with mode defined as
`DSH_TELEMETRY_MODE || 'DISABLED'`. Telemetry is therefore disabled by default
in the observed candidate. The study will set `DSH_TELEMETRY_MODE=DISABLED`
explicitly and verify the composed configuration before every collected run.

## Offline mock integration result

On 2026-08-24, the pinned DSH headless loop completed deterministic runs for the
baseline (`D`), Markdown state (`M`), and ThoughtML state (`T`) conditions.

- All conditions exited successfully and persisted a DSH session.
- Every assembled model request used only the local
  `thoughtml-study-mock/deterministic-v1` route.
- `D` emitted 40 recorded events; a deterministic operation failed once and
  succeeded on its second attempt without any state tool.
- `M` and `T` each emitted 74 recorded events and invoked the matched
  commit/read/inspect sequence between the same failed and successful operation.
- Both formats committed revision 1, retained immutable revisions 1 and 0,
  refreshed DSH's per-step state context, and returned `valid: true` with zero
  diagnostics. The `T` condition used the repository's ThoughtML 0.5.0 strict
  checker.
- The separate aggregate collector recorded one opened and completed recovery
  episode in every condition, plus one post-failure state checkpoint in M and T.
- The production package's 10 offline tests passed, covering restart/resume,
  bounded context, atomic rejection, history, visible-file repair, pointer
  integrity, recovery notices, structured rendering, and metric privacy.
- The child environment contained no DeepSeek credential, telemetry was
  explicitly disabled, and the result records zero network model calls.

This establishes the production DSH plugin, state context, recovery notice,
revision journal, aggregate metrics, raw event log, and session-persistence
seams. It does not establish native coding-tool behavior, benchmark execution,
or the effect of a real model. Those remain later gates.

## Live credential diagnostic

On 2026-08-24, one explicitly authorized development-only request completed
through the pinned DSH headless profile. The request header recorded provider
`deepseek-official` and model `deepseek-v4-flash`; the assistant returned the
required `READY` response. DSH recorded one request, 7,962 input tokens, and
3 output tokens. Telemetry was explicitly disabled. Raw logs remain ignored and
the compact diagnostic record contains no credential.

This verifies authentication and the exact Flash route. It is not a benchmark
task, plugin evaluation, pilot observation, or paper result. The unexpectedly
large fixed input demonstrates why prompt and tool-schema overhead must be
measured during plugin development.

## Live plugin compatibility smoke

After the production package and offline D/M/T lifecycle passed, one separately
authorized development-only ThoughtML session ran on
`deepseek-official/deepseek-v4-flash`. The model followed the required
`reasoning_state_read`, `reasoning_state_commit`, and
`reasoning_state_inspect` sequence without another tool, authored a 1,674-byte
strict-valid ledger, advanced the state to revision 1, and returned
`PLUGIN_READY`. DSH recorded four model calls, 10,287 input tokens, 29,824
cache-read tokens, 1,309 output tokens, and 795 reasoning tokens. Telemetry was
disabled; the credential and raw ignored trajectory are absent from the compact
diagnostic record.

This smoke session exposed an instrumentation omission rather than a state-tool
failure: cached-input and reasoning usage are separate DSH fields. The metrics
collector was expanded to preserve both, and its unit and offline DSH tests were
rerun successfully. This session remains development evidence only and is not a
pilot or agent-utility result.

## Feasibility decision

- **Native Windows DSH integration:** offline state integration passed; native
  coding-tool smoke testing remains.
- **DeepSeek live call:** credential and `deepseek-v4-flash` route verified with
  one development-only request; study collection remains separately gated.
- **Full local SWE-bench:** infeasible in the observed environment.
- **Small SWE-bench subset:** task metadata and DSH integration can be prepared
  locally; official selected-task containers should run on a larger local drive,
  repaired Linux/Docker environment, university machine, or on-demand cloud
  evaluator.

This infrastructure result does not change the scientific three-condition
design. It confirms that the design can be instrumented in DSH and changes only
where selected benchmark containers can execute.
